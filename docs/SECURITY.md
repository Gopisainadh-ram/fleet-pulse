# Security

This project is built against the **OWASP Top 10 (2021)**. The table says what the risk is,
what we do about it, and exactly where to look in the code.

| # | Risk | What we do | Where |
| --- | --- | --- | --- |
| A01 | Broken access control | Every route is behind `authenticate` and `requirePermission`. Permissions are deny-by-default and live in one table. Drivers can only read their own data (looked up by the token's user id, never by an id from the URL). Role hierarchy stops privilege escalation in user management. Admins can't see super admins. | `common/middleware/authorize.ts`, `libs/shared/src/lib/permissions.ts`, `modules/users/user.service.ts` |
| A02 | Cryptographic failures | Passwords hashed with bcrypt (cost 12), never stored or logged in plain text. Invitation tokens are random, stored only as SHA-256 hashes, expire after 24 hours, and are single-use. JWTs signed with separate 32+ char secrets that are validated at startup. Refresh cookie is `Secure` in production. Only the access token (15 min) is exposed to JavaScript. | `modules/auth/auth.service.ts`, `config/env.ts` |
| A03 | Injection | Prisma sends parameterised queries. The one raw SQL query uses a tagged template so values are bound parameters. Every input is validated by zod. Sort columns come from a whitelist (zod enum), never straight from the client. | `*.schema.ts`, `dashboard.service.ts`, `common/middleware/validate.ts` |
| A04 | Insecure design | Rate limits (global and tighter on login). Account lockout. Body size limit. Assignments run in a Serializable transaction so business rules can't be raced. Soft rules over hard deletes where history matters. | `common/middleware/rateLimit.ts`, `vehicle.service.ts` |
| A05 | Security misconfiguration | `helmet` headers, `x-powered-by` off, CORS allow-list (no `*`), strict env validation, generic 500 messages with no stack traces, `.env` ignored by git, seed script refuses to run in production. | `app.ts`, `config/env.ts`, `errorHandler.ts` |
| A06 | Vulnerable and outdated components | Pinned versions in `package.json`. Run `npm run audit` regularly and in CI. Turn on Dependabot or Renovate on the repository. | `package.json` |
| A07 | Identification and authentication failures | Lockout after 5 failed logins (15 min). Same "Invalid email or password" message for unknown user, wrong password, inactive and locked accounts. Dummy hash comparison so timing doesn't reveal whether an email exists. Refresh tokens rotate on every use; reuse of an old one revokes all sessions for that user. Password policy: 12+ chars with upper, lower and digit. Deactivating a user or changing their role/password revokes their sessions. JWT algorithm is pinned to HS256. | `auth.service.ts`, `authenticate.ts`, `user.schema.ts` |
| A08 | Software and data integrity failures | Lockfile committed (`package-lock.json`, generated by `npm install`). No unsafe deserialisation. CSRF defence for the cookie endpoints: `SameSite=Strict`, cookie scoped to `/api/auth`, and a required `X-Requested-With` header. | `csrfHeader.ts`, `auth.controller.ts` |
| A09 | Security logging and monitoring failures | Structured logs (pino) with `Authorization` and cookies redacted. An `audit_logs` table records logins, failures, lockouts, token reuse, and every create / update / delete / assign. | `common/logger.ts`, `common/audit.ts` |
| A10 | Server-side request forgery | The API never fetches a URL supplied by a user. If you add a feature that does (webhooks, image import), validate against an allow-list and block private IP ranges. | n/a today |

## Token flow in plain words

1. **Login.** Server checks the password, then sends back a short-lived **access token**
   (15 minutes) in the response body and a long-lived **refresh token** (7 days) in an
   httpOnly cookie.
2. The Angular app keeps the access token **in memory only** (not localStorage), so a
   script injected into the page can't steal a long-lived credential.
3. When the access token expires the interceptor calls `/auth/refresh`. The server
   **rotates**: the old refresh token is revoked and a new one issued.
4. If an already-used refresh token shows up again, someone probably copied it. The server
   revokes **all** of that user's refresh tokens and logs `auth.refresh_reuse`.
5. Logout revokes the refresh token and clears the cookie.

## Production checklist

- [ ] Serve everything over HTTPS (needed for the `Secure` cookie).
- [ ] Put the web app and API on the same site (for example `app.example.com` and `/api`) so `SameSite=Strict` works.
- [ ] Set `NODE_ENV=production`.
- [ ] Use long random values for both JWT secrets, stored in a secrets manager, not in git.
- [ ] Set `CORS_ORIGIN` to the real web origin only.
- [ ] Use a dedicated database user with only the rights the app needs.
- [ ] Add the optional partial unique indexes from [DATABASE.md](DATABASE.md).
- [ ] Run `npm run audit` in CI and enable automatic dependency updates.
- [ ] Add a CSP header for the web app at your reverse proxy / CDN.
- [ ] Make sure logs are shipped somewhere and someone looks at `auth.*` audit events.
- [ ] Back up the database.

## Known limits (be honest about these)

- Access tokens are stateless, so a deactivated user's access token stays valid until it
  expires (at most 15 minutes). Their refresh tokens are revoked immediately.
- The rate limiter keeps counters in memory. With more than one API instance, switch it to
  a shared store such as Redis.
- Two browser tabs refreshing at the same instant are handled with a 10 second grace
  window. A very unlucky race can still sign one tab out.
- No MFA or self-service password reset in v1. Password setup invitations are supported for new accounts.
